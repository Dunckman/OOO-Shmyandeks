# Паспорт проекта

## Общие сведения

**Название команды:** ООО «Шмяндекс».

**Название продукта:** «Стафф» - сервис выдачи и возврата имущества.

**Репозиторий:** [OOO-Shmyandeks](https://github.com/Dunckman/OOO-Shmyandeks)

**Коды участников:** `M1`, `M2`, `M3`.

**Статус:** в разработке. Текущий результат описан в разделе 9.

## 1. Назначение

«Стафф» предназначен для учета выдачи и возврата инвентаря в учебной организации. Сотрудник фиксирует получателя, срок возврата и состояние предмета, а студент просматривает свои текущие выдачи и историю. Серверная логика контролирует доступность каждого экземпляра: исключает одновременную выдачу нескольким получателям и восстанавливает доступность после возврата, если предмет не требует проверки.

## 2. Граница продукта

**В продукт входят:**

- Серверное HTTP API и база данных одного пункта выдачи
- Вход под учебной учетной записью студента или сотрудника
- Каталог экземпляров с инвентарным номером, названием, описанием состояния и допуском к выдаче
- Выдача конкретного экземпляра студенту с указанием срока возврата
- Возврат с записью состояния предмета и сохранением истории выдачи
- Просмотр своих выдач для студента и всех выдач пункта для сотрудника

**За пределами приложения остаются:**

- Обращение за предметом, его осмотр и физическая передача. Приложение сохраняет сведения о выдаче и возврате
- HTTP-клиент или браузерная страница API, через которые пользователи отправляют запросы
- Университетские системы: интеграция для входа и получения данных студентов не предусмотрена. Учебные учетные записи и роли создаются при подготовке локального стенда

**В первую версию не входят:**

- Бронирование, очередь заявок и согласование заявок
- Оплата, залоги, штрафы и расчет ущерба
- Несколько складов, доставка, закупки и учет ремонта
- Самостоятельная регистрация, восстановление пароля по почте и SSO
- Загрузка фотографий и файлов, QR-коды, уведомления и мобильное приложение

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать                                                                                                                                                     | Что ему недоступно                                                                                                                                           |
| --- | --- |----------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `USER` | Получатель инвентаря | Просматривать каталог, читать свои активные и завершенные выдачи, сроки и состояние предметов                                                                        | Читать чужие выдачи; оформлять выдачу или подтверждать возврат; изменять каталог, сроки, получателя и роли                                                   |
| `STAFF` | Пользователь, ответственный за передачу и прием имущества | Создавать и редактировать карточки экземпляров, изменять допуск, выбирать студента из учебных учетных записей, оформлять выдачи и возвраты, читать все выдачи пункта | Назначать роли через API; удалять историю; изменять получателя, экземпляр и срок уже оформленной выдачи, выдавать занятый или не допущенный к выдаче предмет |
| Пользователь без входа | Пользователь, не прошедший аутентификацию | Отправить запрос входа                                                                                                                                               | Читать данные каталога и выдач или изменять их                                                                                                               |

Инвентарный номер задаётся при создании карточки и затем не меняется через API,
чтобы предмет сохранял тот же номер в истории выдач. Сотрудник может менять
название, текущее описание состояния и допуск. Эти изменения не переписывают
описания состояния, сохранённые при выдаче и возврате.

Каталог отдельно показывает допуск, занятость и доступность для новой выдачи.
Предмет занят, если у него есть активная выдача; он доступен, только если допущен
и не занят. Сведения о получателе в каталог не входят. Доступность в каталоге
отражает состояние на момент чтения: перед выдачей сервер проверяет её заново.

## 4. Сквозные сценарии

### Сценарий 1. Выдача инвентаря

- **Участники:** студент и сотрудник пункта выдачи
- **Начальное условие:** у обоих участников есть учебные учетные записи; выбранный экземпляр находится в каталоге, допущен к выдаче и не связан с активной выдачей
- **Основные действия:**
  1. Студент входит в систему, просматривает каталог и обращается к сотруднику за выбранным предметом
  2. Сотрудник выбирает экземпляр и студента, указывает срок возврата и состояние предмета
  3. Сервер проверяет роль `STAFF`, наличие учетной записи студента, срок и доступность экземпляра. Выдача сохраняется только при выполнении всех условий
  4. Сотрудник получает подтверждение и передает предмет. Студент видит новую выдачу и срок в своем списке
- **Результат:** экземпляр закреплен за студентом и недоступен для другой выдачи
- **Какие данные или состояние изменяются:** создается активная выдача с экземпляром, получателем, сроком, состоянием при передаче, временем операции и сотрудником. Наличие этой записи определяет занятость экземпляра
- **Условия отказа:** экземпляр не найден, уже занят или не допущен к выдаче; получатель не найден или не имеет роли `USER`; срок возврата не позже времени выдачи. Сервер отклоняет операцию без изменения данных. При двух одновременных попытках выдать один экземпляр успешной может быть только одна

### Сценарий 2. Возврат инвентаря

- **Участники:** студент и сотрудник пункта выдачи
- **Начальное условие:** у студента есть активная выдача, и он приносит предмет обратно
- **Основные действия:**
  1. Студент находит свою выдачу и передает предмет сотруднику для осмотра
  2. Сотрудник находит активную выдачу, сверяет инвентарный номер, записывает состояние предмета и отмечает, можно ли выдать его снова
  3. Сервер проверяет роль `STAFF` и активное состояние выдачи. Возврат, текущее описание состояния предмета и допуск к следующей выдаче сохраняются в рамках одной операции
  4. Студент видит закрытую выдачу в истории. Сотрудник видит предмет доступным или требующим проверки
- **Результат:** возврат записан, активная выдача закрыта, история сохранена
- **Какие данные или состояние изменяются:** фиксируются время возврата, принявший сотрудник и состояние предмета. Описание состояния при возврате также становится текущим описанием в карточке предмета. Если предмет требует проверки, новая выдача недоступна до восстановления допуска сотрудником
- **Условия отказа:** выдача не существует или уже закрыта. Сервер отклоняет запрос без изменения данных. Студент не может подтвердить возврат самостоятельно. Просрочка не препятствует приему предмета сотрудником

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия                                                                   | Последствия неправильного изменения, удаления или недоступности                                                                                |
| --- | --- |-----------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Учетная запись: учебный логин, данные проверки пароля и роль | Для владельца записи и сотрудника | Утечка данных доступа может привести к входу под чужой учетной записью                  | Подмена роли дает лишние права, подмена записи нарушает связь со студентом, недоступность препятствует входу                                   |
| Экземпляр: инвентарный номер, название, состояние и допуск | Для студентов и сотрудника | Становится известен состав имущества пункта, сведения о получателях в каталог не входят | Неверный номер связывает выдачу с другим предметом, ложный допуск позволяет выдать неисправный предмет, потеря карточки мешает учету           |
| Выдача: экземпляр, получатель, срок, время и состояние при передаче и возврате, сотрудники | Для получателя и сотрудника | Посторонний узнает, кто, когда и чем пользовался                                        | Подмена получателя приписывает человеку чужую выдачу, ложный возврат скрывает невозвращенный предмет, потеря истории мешает проверить передачу |

## 6. Компоненты и внешние взаимодействия

Структура включает одно серверное приложение на Kotlin со Spring Boot и одну базу данных PostgreSQL. Для доступа к данным выбраны Spring Data JPA и Hibernate как реализация JPA. Liquibase применяет миграции при запуске, Hibernate проверяет соответствие сущностей схеме.

| Компонент                               | Назначение | Основные взаимодействия и данные                                                                                                    |
|-----------------------------------------| --- |-------------------------------------------------------------------------------------------------------------------------------------|
| HTTP-клиент или браузерная страница API | Выполнение пользовательских действий | Отправляет данные входа, ID экземпляра, выдачи или получателя, срок и описания состояния, получает каталог, выдачи и результаты операций                  |
| Сервер приложения                       | Проверка пользователя и выполнение предметных операций | Принимает HTTP-запрос, читает и сохраняет учетные записи, экземпляры и выдачи в БД, возвращает только доступные пользователю данные |
| PostgreSQL                              | Постоянное хранение данных | Получает запросы от сервера и локальной процедуры подготовки стенда                                                                 |
| Автоматизация подготовки стенда         | Создание схемы БД и учебных данных | Добавляет учетные записи с ролями и несколько экземпляров, запуск через публичное API не предусмотрен                               |

Данные проходят от клиента к серверу, затем к БД и обратно через сервер. Прямой доступ клиента к БД не предусмотрен. Сервер определяет текущего пользователя и его роль по результату аутентификации, а не по полю роли в запросе. Для основных сценариев не требуются отдельные фоновые сервисы, брокер сообщений и сторонние API

| Начальный учебный набор | Два студента, сотрудник и несколько предметов | Команда проекта | Создает воспроизводимые исходные данные для демонстрации |
| Сохраненные записи БД | Активная выдача и допуск экземпляра | Сервер и процедура подготовки стенда | Проверяет доступность и возможность следующей операции |
| Часы сервера | Текущее время | Локальное окружение запуска | Фиксирует время выдачи и возврата, определяет просрочку |

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- Вход под учебными учетными записями, проверка роли и принадлежности выдачи
- Каталог экземпляров, редактирование карточек и допуска сотрудником
- Оформление выдачи с проверкой доступности, получателя и срока, записью состояния предмета
- Возврат через сотрудника с записью состояния и правильным обновлением доступности
- Просмотр студентом своих выдач, сотрудником - всех выдач пункта
- Сохранение данных после перезапуска и подготовка локального учебного стенда

**Функции, которые можно исключить при нехватке времени:**

- Отдельный пользовательский интерфейс: останется работа через API
- Поиск по названию и дополнительные фильтры каталога
- Отдельная сводка просрочек: срок и состояние каждой выдачи останутся видны в ее карточке

Исключение дополнительных функций сохраняет оба сквозных сценария, различия полномочий пользователей и работу с постоянным хранилищем

## 9. Стек и путь к первой работающей версии

**Основные технологии:**

| Технология | Назначение                                                                           |
| --- |--------------------------------------------------------------------------------------|
| Kotlin/JVM | Язык серверного приложения, выполнение на JVM                                        |
| Spring Boot | Настройка и запуск приложения, подключение БД и Liquibase                           |
| Spring Framework | Обработка HTTP-запросов, организация серверных компонентов и управление транзакциями |
| Spring Data JPA | Репозитории для чтения и сохранения сущностей                                        |
| Hibernate ORM | Реализация JPA, отображение сущностей на таблицы и выполнение операций с БД          |
| PostgreSQL | Хранение учетных записей, экземпляров и истории выдач                                |
| Liquibase | Создание и последовательное изменение схемы БД при запуске приложения                |

Для первой версии запланировано HTTP API без отдельного frontend. Основа приложения использует JDK 21, Kotlin 2.3.21 и Spring Boot 4.1.1. Версии закреплены в `staff/pom.xml`, Maven 3.9.16 — в `staff/.mvn/wrapper/maven-wrapper.properties`. Для локальной БД и тестов используется образ `postgres:latest`. Пароль локальной БД хранится в `staff/.env`, который исключен из Git; шаблон настроек — `staff/.env.example`.

**Технологии, новые для команды:** Для участников `M1`, `M2` Spring Data JPA и Hibernate ORM являются новыми технологиями

**Внешние сервисы, необходимые для запуска:** локальный экземпляр PostgreSQL. Облачные API, почтовый сервис и университетский SSO не используются. Доступ к интернету необходим для первоначальной установки инструментов и зависимостей

**Работа при недоступности внешних сервисов:** после установки JDK, PostgreSQL и загрузки зависимостей сервер и БД запускаются локально. При использовании Docker образ БД тоже нужно загрузить заранее. Подготовлен отдельный скрипт на три учебных предмета; создание учебных аккаунтов и проверки выдачи и возврата через HTTP будут добавлены вместе с соответствующими операциями

**Первый технический результат:** реализован запуск Spring Boot с PostgreSQL, миграциями Liquibase и JPA-сущностями учетной записи, экземпляра и выдачи. Схема содержит связи и ограничения, включая запрет двух активных выдач одного экземпляра. Отдельный SQL-скрипт добавляет три предмета. Следующий шаг — OpenAPI и каркас контроллеров, затем чтение каталога из БД с учетом требований входа. Вход, выдача и возврат пока не реализованы
