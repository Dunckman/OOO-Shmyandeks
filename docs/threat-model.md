# Модель угроз

Модель относится к текущей версии продукта «Стафф» и построена по актуальным
[`PROJECT.md`](../PROJECT.md) и
[`docs/security-requirements.md`](security-requirements.md).

Цель модели — показать, каким реалистичным способом могут быть нарушены свойства,
зафиксированные в `SR-*`, и выделить приоритетные угрозы для проектных решений.

> Источником истины для этой версии модели являются документы, находящиеся в
> командном репозитории. Если сценарии, роли, состояния или API меняются,
> сначала согласованно обновляются паспорт и требования безопасности, после
> чего пересматриваются затронутые `T-*`.

## 1. Модель продукта

### 1.1. Архитектурный вид

Текущая версия предусматривает один сервер приложения и одну базу данных.

```mermaid
flowchart LR
    U[USER]
    S[STAFF]
    C[HTTP-клиент / браузерная страница API]

    subgraph SYSTEM[Контур продукта]
        API[Сервер приложения<br/>Kotlin + Spring]
        DB[(PostgreSQL)]
    end

    INIT[Локальный скрипт<br/>подготовки данных]

    U --> C
    S --> C

    C -->|HTTP: данные входа, ID,<br/>сроки, состояние предмета,<br/>команды чтения и изменения| API
    API -->|каталог, выдачи,<br/>результаты операций и ошибки| C

    API -->|миграции Liquibase при запуске;<br/>чтение и изменение данных| DB
    DB -->|сохранённое состояние| API

    INIT -->|сейчас: три предмета;<br/>учебные аккаунты и роли — план| DB
```

Главная публичная точка входа — HTTP API. Пользователь управляет HTTP-клиентом
и может сформировать запрос независимо от ограничений пользовательского
интерфейса. Сервер приложения самостоятельно принимает решения об
аутентификации, роли, принадлежности выдачи, допустимости изменения состояния и
согласованности предметной операции.

Прямой доступ пользовательского клиента к PostgreSQL не предусмотрен. База
данных изменяется сервером приложения и локальной процедурой подготовки стенда.

### 1.2. Что уже существует

В репозитории зафиксированы:

- паспорт продукта `PROJECT.md`;
- требования безопасности `SR-01`–`SR-11`;
- роли `USER` и `STAFF`, их полномочия и два основных сквозных сценария;
- планируемый технологический стек;
- правила локального учебного стенда.

В коде есть запускаемая основа Spring Boot с PostgreSQL, миграциями
Liquibase, JPA-сущностями учетной записи, предмета и выдачи. Отдельный скрипт
добавляет три предмета. Есть OpenAPI, контроллеры, правила доступа Spring Security,
проверка работы приложения и получение CSRF-токена. Реализовано чтение списка
предметов из БД с пагинацией, занятостью и доступностью. Вход и остальные
предметные операции пока остаются заглушками.
[Запуск](../PROJECT.md#10-локальный-запуск) описан в паспорте; существующие
[интеграционные тесты](../staff/src/test/kotlin/org/shmyandeks/staff/StaffApplicationTests.kt)
проверяют схему БД, JPA и скрипт наполнения.

### 1.3. Что пока планируется

Планируется реализовать:

- вход под учебными учётными записями;
- проверку принадлежности выдачи;
- чтение отдельной карточки, создание и редактирование предметов;
- получение списка учебных аккаунтов студентов;
- оформление выдачи и возврата;
- работу предметных операций с уже созданной схемой PostgreSQL;
- подготовку учебных аккаунтов;
- ограничение попыток входа;
- безопасное хранение паролей;
- защищённый транспорт для случая удалённого доступа.

Механизмы реализации описаны в [проектных решениях](design-decisions.md)
`D-01`–`D-06`.

### 1.4. Существенные допущения

1. Рассматривается одна учебная организация и один пункт выдачи.
2. Публичная регистрация, восстановление пароля, SSO, загрузка файлов,
   платежи, QR-коды, уведомления и мобильное приложение отсутствуют.
3. Учебные аккаунты и роли создаются процедурой подготовки стенда, а не
   публичным API.
4. Клиентская сторона недоверенна: отсутствие кнопки или скрытое поле в интерфейсе не
   мешает пользователю отправить произвольный HTTP-запрос.
5. Знание ID предмета или выдачи не подтверждает право доступа или
   право изменения.
6. Для локального стенда HTTP допустим только при условии, что API недоступен
   другим устройствам. При удалённой демонстрации действуют `SR-09` и `D-06`: HTTPS
   с первого запроса, проверка сертификата клиентом и доступ только с разрешённых
   компьютеров учебного стенда. Публичный доступ из интернета не предусмотрен.
7. Время предметных событий определяется серверной стороной.
8. Текущий паспорт описывает оформление `STAFF` сразу активной выдачи и
   последующий возврат. Другие состояния и переходы не включаются в эту модель,
   пока они не появятся в актуальных `PROJECT.md` и `security-requirements.md`.

## 2. Границы доверия

| ID | Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- | --- |
| `TB-01` | Пользовательский клиент и сеть → сервер приложения | Логин и пароль, ID предметов и выдач, параметры чтения, получатель, срок, состояние предмета, команды изменения; в обратную сторону — каталог, выдачи и результаты операций | Клиент управляется пользователем, а при удалённом доступе сеть также нельзя считать доверенной. Корректный формат запроса не доказывает полномочия, принадлежность объекта или допустимость операции. Сервер обязан сам установить пользователя, роль, право на объект и допустимость изменения. |
| `TB-02` | Подготовка стенда: Liquibase при запуске приложения и локальный скрипт → PostgreSQL | Миграции схемы и начальные предметы; учебные аккаунты, роли и хеши паролей — после реализации их подготовки | Процедура подготовки стенда имеет привилегированный путь записи, минующий публичный API. Ошибка в ней способна создать неверные роли, слабые данные проверки пароля или некорректное исходное состояние. |

Связь сервер приложения → PostgreSQL не выделяется как отдельная граница
доверия при условии, что стендом управляет команда, файлы и данные подключения
недоступны посторонним, а порт БД открыт только на `127.0.0.1`. Сейчас приложение
и Liquibase используют одну учётную запись БД; разделение их прав не реализовано.
Данные из БД не заменяют проверку роли и принадлежности выдачи на сервере.
Атомарность и ограничения БД существенны для `T-05` и `T-06`. При изменении
доступа к БД эти допущения и границу нужно пересмотреть.

## 3. Значимые объекты и свойства

Основные объекты определены в разделе 5 [паспорта проекта](../PROJECT.md).

Для модели угроз существенны следующие свойства:

- **учётная запись** — нельзя позволить войти от имени другого пользователя,
  назначить себе роль или раскрыть данные проверки пароля;
- **выдача** — `USER` не должен видеть чужие записи; получатель, предмет,
  исходные сведения и история возврата не должны произвольно подменяться;
- **экземпляр имущества** — нельзя допустить одновременно несколько активных
  выдач одного экземпляра или выдачу предмета без допуска;
- **история операций** — завершённая выдача не должна переписываться повторным
  или запоздалым запросом;
- **секреты и диагностические данные** — пароли, сохранённые проверочные
  значения, ключи и внутренние детали ошибок не должны раскрываться;
- **сетевой обмен** — при удалённом доступе третья сторона не должна читать или
  незаметно изменять данные входа и предметные операции.

## 4. Угрозы

Если для отдельного маршрута отсутствует обязательная проверка входа, сервер возвращает данные или выполняет действие без установленной личности пользователя. | Требование обязательной аутентификации; конфиденциальность предметных данных и возможность безопасно связывать действие с пользователем. | `TB-01`, любой защищённый маршрут API | `SR-01` | **Высокий, приоритетный.** Это нарушение основной границы доверия: атакующему не нужны ни чужой ID, ни повышенная роль. | `T-05` | Один пользователь с ролью `STAFF` почти одновременно отправляет два запроса на выдачу одного свободного экземпляра разным `USER`. Оба запроса успевают прочитать предмет как свободный до сохранения первого результата. Если проверка доступности и создание выдачи не согласованы атомарно, появляются две активные выдачи одного предмета. Аналогично сбой между фиксацией возврата и изменением описания состояния или допуска предмета может оставить частичное состояние. | Уникальность активной выдачи, целостность учёта и атомарность изменения связанных данных. | `TB-01`, создание выдачи и возврат; внутренняя запись состояния в PostgreSQL | `SR-05` | **Высокий, приоритетный.** Угроза возникает из двух корректных запросов и затрагивает центральный инвариант продукта. Она должна повлиять на решения по транзакциям и ограничениям состояния. |

Атака проста и не требует учётной записи, но её практическая поверхность сейчас ограничена локальным режимом. |

## 5. Приоритетный набор

Основной набор для проектных решений:

- `T-01` — доступ к защищённым данным или операциям без аутентификации;
- `T-02` — прямой вызов операций `STAFF` и попытка повысить полномочия;
- `T-03` — доступ `USER` к чужой выдаче по ID;
- `T-05` — двойная выдача и частичное состояние при конкурентных операциях;
- `T-06` — повторный или конкурентный возврат с искажением истории.

Этот набор выбран потому, что угрозы относятся к основной границе доверия и двум
сквозным сценариям — выдаче и возврату. Они затрагивают установление личности,
полномочия, принадлежность данных и наиболее важные инварианты состояния. Все
пять должны влиять на архитектурные решения уже при создании серверной основы.
`T-04` после проверки роли касается полей разрешённой операции `STAFF`,
а `T-10` требует предварительной утечки БД. Для `T-08` нужны отдельные проверки
ответов и секретов. Эти угрозы также разобраны в `D-04` и `D-05`, но основной
набор выбран для общей политики доступа и согласованности выдачи и возврата.

Остальные `T-*` сохраняются в модели. Их отсутствие в текущем приоритетном
наборе не отменяет соответствующие `SR-*`. Условия удалённой демонстрации
для `T-09` и ограничения защиты от `T-11` зафиксированы в `D-05` и `D-06`.
