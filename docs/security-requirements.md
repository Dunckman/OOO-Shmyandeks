# Требования безопасности

«Стафф» — сервис выдачи и возврата инвентаря. Требования основаны на [паспорте проекта](../PROJECT.md): студент читает каталог и свои выдачи, сотрудник оформляет выдачу и возврат. Требования защищают сведения о студентах и историю передачи вещей, так как ошибка в учёте может назначить другого получателя, скрыть возврат или позволить повторно выдать уже занятый предмет.

Ниже описаны ожидаемые результаты проверок. 

| ID | Требование | Критерий приёмки | Связанные T / D (позднее) |
| --- | --- | --- | --- |
| SR-01 | Каталог и выдачи доступны только после входа под учебной учётной записью. Ошибка входа не должна раскрывать, существует ли указанный логин. | Запросы чтения каталога и выдач, оформления выдачи и возврата без действующей аутентификации получают `401` без предметных данных. До достижения лимита SR-11 неверный пароль и неизвестный логин дают одинаковые `401` и сообщение об ошибке. После успешного входа студент может прочитать каталог и свои выдачи. | — |
| SR-02 | Только сотрудник может изменять каталог и допуск предметов, выбирать получателей из учебных учётных записей, оформлять выдачу и возврат. Роли задаются при подготовке стенда и не меняются через API. | Студент читает каталог, но при попытке изменить карточку, допуск, получить список получателей, оформить выдачу или возврат получает `403`, в том числе для своей выдачи. Переданная в запросе роль сотрудника не даёт ему дополнительных прав. Ни студент, ни сотрудник не могут назначить роль через API. Сотрудник с корректными данными успешно оформляет выдачу и возврат; изменения видны при повторном чтении. | — |
| SR-03 | Студент видит только свои активные и завершённые выдачи. Знание ID чужой выдачи не даёт доступа к ней; каталог не раскрывает сведения о получателях. | Студент B запрашивает активную или завершённую выдачу A — получает `404` без её содержимого. В списке B и, если они предусмотрены, на всех его страницах и в общем количестве учитываются только записи B. Подстановка чужого ID в параметры запроса не раскрывает чужие записи. A может прочитать свою выдачу, сотрудник — выдачи обоих студентов. В каталоге нет данных о том, кто получал предмет. | — |
| SR-04 | Исполнителя, время выдачи и возврата определяет сервер. Получатель, экземпляр, срок и состояние при передаче сохраняются при оформлении выдачи и затем не меняются. | При выдаче и возврате сохраняются вошедший сотрудник и время сервера. Запрос с подставленным исполнителем или временем отклоняется с `400`. Попытка вместе с возвратом изменить получателя, экземпляр, срок или состояние при передаче также даёт `400`. Через API нельзя изменить эти сведения у уже оформленной выдачи, в том числе от имени сотрудника. Изменение карточки предмета не переписывает сохранённое состояние при передаче. | — |
| SR-05 | На один экземпляр может приходиться только одна активная выдача, в том числе при одновременных запросах. Возврат и изменение допуска предмета должны сохраняться вместе. | Сотрудник отправляет два одновременных запроса на выдачу одного доступного предмета разным студентам: один запрос успешен, второй получает `409`. В базе остаётся одна активная выдача. При ошибке сохранения новая выдача не появляется. Если ошибка происходит при возврате, выдача остаётся активной, сведения о возврате не появляются и допуск предмета не меняется. | — |
| SR-06 | Возврат закрывает только активную выдачу. Повторный запрос не должен переписывать историю или освобождать предмет из другой выдачи. Завершённые записи нельзя изменять или удалять через API. | Повтор возврата получает `409`. Дата и время ранее выполненной операции не меняются; повтор старого возврата не затрагивает новую выдачу того же предмета. При двух одновременных возвратах один запрос успешен, второй получает `409`, сохраняется один результат. Ни студент, ни сотрудник не могут изменить или удалить завершённую запись. История сохраняется после перезапуска. Корректный возврат просроченной активной выдачи проходит успешно. | — |
| SR-07 | Предмет без допуска нельзя выдать студенту. Если при возврате сотрудник отмечает, что вещь требует проверки, новая выдача запрещена до снятия этой отметки сотрудником. | Попытка выдать предмет без допуска получает `409`. После возврата с отметкой о необходимости проверки выдача закрыта, состояние вещи сохранено, повторная выдача получает `409`. Студент не может снять отметку. После восстановления допуска сотрудником свободный предмет можно выдать снова. | — |
| SR-08 | Данные проверки паролей и другие секреты не должны попадать в ответы о каталоге и выдачах, сообщения об ошибках и репозиторий. | В ответах студенту и сотруднику нет паролей, их сохранённых проверочных значений и секретов доступа. Искусственно вызванная внутренняя ошибка возвращает `500` без SQL, стека вызовов и секретов. В публикуемых файлах и истории Git нет действующих паролей и ключей; в примерах конфигурации используются заглушки. | — |
| SR-09 | Данные входа и выдач должны быть защищены от перехвата и подмены при передаче между компьютерами. HTTP разрешён только для учебного запуска, когда клиент и сервер находятся на одном компьютере, а API недоступен другим устройствам. | Локальный стенд доступен с компьютера, на котором запущен, но недоступен другим устройствам. При удалённом доступе корректные запросы по HTTPS выполняются; клиент отклоняет недействительный сертификат. Удалённый запрос по HTTP не позволяет войти, выполнить защищённую операцию или получить данные выдач. Данные входа и содержимое ответа не видны в открытом сетевом обмене. | — |
| SR-10 | При утечке базы хранение паролей должно затруднять их подбор. Для этого используется специализированный алгоритм хеширования паролей с отдельной случайной солью и параметрами не ниже рекомендованных OWASP для выбранного алгоритма. Обычный SHA-256 с солью, открытый текст и обратимое шифрование не допускаются. | Проверка библиотеки, кода подготовки учебных аккаунтов, настроек и сохранённых значений подтверждает использование подходящего по [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#password-hashing-algorithms) алгоритма и рекомендованных параметров. Например, для Argon2id подходит профиль: не менее 19 МиБ памяти, не менее двух проходов, параллелизм 1. У двух учебных аккаунтов с одинаковым паролем соли и хеши различаются; исходные пароли и их обратимо зашифрованные копии не сохраняются. Для каждого аккаунта правильный пароль позволяет войти, неправильный даёт `401`, если лимит SR-11 не достигнут. | — |
| SR-11 | Сервер должен ограничивать подбор пароля: не более пяти попыток входа для одного логина за любую минуту, независимо от IP отправителя. Это ограничение одинаково для существующих и неизвестных логинов и не блокирует вход других пользователей. | Первые пять запросов с неверным паролем получают `401`; шестой запрос для того же логина в течение минуты — `429`, даже с другого IP и с правильным паролем. Вход не выполняется; сервер сообщает время до разрешённой попытки. Через 60 секунд после последней учтённой попытки правильные данные снова позволяют войти. Отклонённые с `429` запросы не продлевают ожидание; другой логин с неизрасходованным лимитом может войти. | — |

**Приоритеты для локальной учебной версии:**

- Высокий — SR-01–SR-08 и SR-10. Нарушение открывает чужие данные, позволяет действовать от чужого имени, искажает учёт или допускает выдачу предмета, требующего проверки.
- Средний — SR-09 и SR-11 при запуске на одном компьютере без доступа извне. Перед открытием стенда для удалённого доступа оба требования получают высокий приоритет и должны быть проверены.

Приоритет задаёт очередность внимания и проверки, а не отменяет требование. 

Для SR-03 использован пункт [OWASP ASVS v5.0.0-8.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md#v82-general-authorization-design) о доступе к конкретному объекту. В нашем случае сервер должен проверять получателя выдачи даже при прямом запросе по её ID.

SR-09–SR-11 уточняют условия учебного стенда, которые не определены в паспорте. При формулировке SR-10 и SR-11 использованы рекомендации OWASP по [хранению паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) и [ограничению попыток входа](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling). Порог в пять попыток за минуту выбран для нашего учебного проекта.
