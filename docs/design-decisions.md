# Проектные решения безопасности

Документ фиксирует проектные решения безопасности «Стафф» по итогам S04 и
опирается на актуальные [`PROJECT.md`](../PROJECT.md),
[`docs/security-requirements.md`](security-requirements.md) и
[`docs/threat-model.md`](threat-model.md).

Текущий набор должен закрыть весь приоритетный набор угроз S03:

- `T-01` — доступ к защищённым данным или операциям без аутентификации;
- `T-02` — обход полномочий `STAFF`;
- `T-03` — доступ студента к чужой выдаче;
- `T-05` — двойная выдача одного экземпляра и частичное состояние;
- `T-06` — повторный или конкурентный возврат с искажением истории.

Будущие проверки ниже — планы проверки механизмов, а не уже выполненные тесты
или свидетельства.

На этапе основы БД реализованы миграции и JPA-сущности. Частичный уникальный
индекс из D-02 уже добавлен в схему. [Интеграционные тесты](../staff/src/test/kotlin/org/shmyandeks/staff/StaffApplicationTests.kt)
проверяют ограничения БД и отображение сущностей. Серверные проверки D-01,
транзакционные операции выдачи и возврата D-02/D-03 пока не реализованы.

## D-01. Единая серверная аутентификация и авторизация на объект

**Контекст:** HTTP-клиент находится за границей доверия. Пользователь может
вручную вызвать любой маршрут, изменить параметры запроса и передать поля,
которых нет в обычном интерфейсе. Поэтому наличие кнопки в UI, переданный
`role`, знание `loanId` и другие клиентские данные не подтверждают право
доступа.

Для `T-01`, `T-02` и `T-03` сервер должен отдельно гарантировать:

1. предметный маршрут нельзя выполнить без установленной личности;
2. операции сотрудника нельзя выполнить от имени `USER`;
3. студент не получает чужую выдачу даже по известному ID.

**Решение:** аутентификация и первичная проверка роли выполняются
централизованно через Spring Security до вызова предметной операции.

После успешного входа текущий пользователь и его роль берутся только из
серверного principal / `SecurityContext`. Поля `userId`, `currentUser`, `role`
и их аналоги из запроса не используются как источник личности или полномочий.

Предметные маршруты закрыты по умолчанию; публичным остаётся только явно
выделенный минимальный набор, необходимый для входа и технического запуска.
Staff-only операции дополнительно проверяются по роли `STAFF` на сервере.

Для доступа студента к выдачам применяется объектная авторизация:

- список `USER` строится с обязательным фильтром по ID текущего пользователя;
- отдельная выдача ищется по паре
  `(loanId, borrowerId=currentUserId)`, а не только по `loanId`;
- если такой записи нет, возвращается `404`;
- `STAFF` использует отдельную разрешённую ветку чтения всех выдач пункта.

Конкретный формат состояния аутентификации между запросами — сессия,
bearer-токен и т.п. — этим D не фиксируется. Существенны серверный источник
principal, закрытые по умолчанию маршруты и обязательная объектная проверка.

**Обоснование:** проверка только в клиентском интерфейсе не является защитой,
потому что запрос можно сформировать вручную. Проверки только роли тоже
недостаточно: два пользователя с ролью `USER` имеют разные права на конкретные
Loan.

Централизованная политика Spring Security уменьшает риск случайно оставить
новый endpoint публичным. Привязка выборки Loan к аутентифицированному
`borrowerId` делает принадлежность частью серверного запроса к данным, а не
проверкой, зависящей от клиента.

`404` для чужой выдачи выбран в соответствии с `SR-03`, чтобы не различать
«записи нет» и «запись существует, но принадлежит другому студенту».

**Связанные угрозы:** `T-01`, `T-02`, `T-03`.

**Связанные требования:** `SR-01`, `SR-02`, `SR-03`.

**Будущая проверка:**

- **Условие:** в стенде есть студент A, студент B, сотрудник и выдача A.
- **Действие:**
  1. без аутентификации запросить каталог, выдачи и staff-only операцию;
  2. войти как B и вызвать staff-only операцию, передав в запросе
     `role=STAFF`;
  3. от имени B запросить выдачу A по известному ID и проверить список B;
  4. от имени A и `STAFF` запросить ту же выдачу.
- **Ожидаемый результат:** запросы без входа получают `401`; B не получает
  права сотрудника и получает `403` на staff-only операцию; чужая выдача для B
  даёт `404`, а его список содержит только собственные записи; A и `STAFF`
  получают разрешённые данные. Клиентские значения роли и пользователя не
  меняют серверную идентичность.

**Ограничения и последствия:**

- новые предметные маршруты должны автоматически попадать под закрытую
  политику;
- service-методы не должны принимать текущего пользователя или роль как
  доверенные значения из DTO;
- проверка роли не заменяет проверку владельца Loan;
- `SR-10` и `SR-11` требуют отдельных механизмов хранения паролей и ограничения
  попыток входа.

## D-02. Инвариант одной активной выдачи обеспечивается транзакцией и БД

**Контекст:** обычная последовательность
«прочитать свободный предмет → проверить отсутствие активной выдачи → вставить
Loan» небезопасна при конкуренции. Два запроса могут одновременно увидеть
старое свободное состояние и оба пройти прикладную проверку. Это сценарий
`T-05`.

**Решение:** оформление выдачи выполняется одной транзакцией Spring, а
ограничение «не более одной активной выдачи на экземпляр» дополнительно
закрепляется в PostgreSQL.

Для текущей модели активна выдача, у которой возврат ещё не зафиксирован.
В миграции создаётся уникальное ограничение, эквивалентное:

```sql
CREATE UNIQUE INDEX uq_active_loan_per_item
    ON loan (item_id)
    WHERE returned_at IS NULL;
```

Точные имена таблиц и колонок могут отличаться; обязательна сама гарантия:
для одного `item_id` одновременно существует не более одной незавершённой
выдачи.

Операция выдачи выполняется так:

1. сервер получает текущего `STAFF` согласно `D-01`;
2. загружает Item для изменения и получает блокировку строки
   (`SELECT ... FOR UPDATE` / `PESSIMISTIC_WRITE`) либо эквивалентную
   сериализацию;
3. под блокировкой повторно проверяет допуск предмета, получателя и срок;
4. создаёт Loan;
5. фиксирует транзакцию.

Операции, меняющие допуск того же Item, должны использовать совместимый
порядок блокировок. Если два запроса всё же конкурируют на вставке, ограничение
PostgreSQL остаётся последней гарантией: одна транзакция успешна, вторая
откатывается, а клиент получает предметный `409`, а не вторую выдачу.

**Обоснование:** транзакция обеспечивает атомарность одного запроса, но сама по
себе не гарантирует уникальность между конкурентными транзакциями. Поэтому
инвариант закрепляется на двух уровнях:

- блокировка Item позволяет перепроверить состояние перед изменением;
- unique-ограничение БД не позволяет физически сохранить две активные выдачи.

Только `existsByItem...` не выбран из-за окна гонки между проверкой и вставкой.
Только синхронизация внутри JVM тоже недостаточна: она не закрепляет инвариант
в хранилище и плохо переносится на несколько процессов приложения.

**Связанные угрозы:** `T-05`; дополнительно частично `T-07`.

**Связанные требования:** `SR-05`; дополнительно `SR-07`.

**Будущая проверка:**

- **Условие:** есть один свободный допущенный предмет и два студента; тест
  выполняется с настоящим PostgreSQL.
- **Действие:** одновременно отправить два запроса `STAFF` на выдачу одного
  Item разным студентам.
- **Ожидаемый результат:** ровно один запрос создаёт выдачу; второй получает
  `409`; в БД после завершения запросов существует ровно одна активная запись
  для этого `item_id`; внутренняя ошибка уникального индекса не раскрывается.

Дополнительно нужно конкурентно изменить допуск предмета и оформить выдачу.
Итог должен соответствовать актуальному состоянию допуска на момент фиксации
транзакции.

**Ограничения и последствия:**

- конкурентную проверку нужно выполнять с PostgreSQL; другая тестовая СУБД
  может не подтвердить семантику частичного индекса и блокировок;
- нарушение именно предметного unique-ограничения должно преобразовываться в
  `409`; не любая ошибка целостности БД означает конфликт выдачи;
- блокировки могут кратковременно увеличивать задержку, что приемлемо для
  учебного пункта выдачи;
- если модель статусов Loan изменится, условие индекса нужно пересмотреть
  вместе с `SR-05` и threat model.

## D-03. Возврат — однократный переход состояния в одной транзакции

**Контекст:** возврат одновременно завершает выдачу и меняет дальнейший допуск
Item. Повторный, запоздалый или конкурентный запрос не должен переписывать
историю и тем более менять состояние предмета после новой выдачи. Это
`T-06` и часть атомарности `SR-05`.

Проверки `if (loan.active)` до сохранения недостаточно: два потока могут
прочитать активное состояние до фиксации первого возврата.

**Решение:** возврат реализуется как один переход `active → completed` внутри
одной транзакции.

Алгоритм:

1. сервер проверяет `STAFF` согласно `D-01`;
2. загружает Loan с блокировкой для записи;
3. после блокировки повторно проверяет, что Loan ещё активен;
4. для активной выдачи загружает и блокирует связанный Item;
5. сервер сам задаёт время возврата и сотрудника;
6. сохраняет осмотр и новый допуск Item;
7. завершает Loan;
8. фиксирует обе части одной транзакцией.

Если Loan уже закрыт, операция завершается с `409` до изменения Item. Второй
конкурентный запрос после ожидания блокировки увидит завершённое состояние и
также получит `409`.

Если предмет уже успели выдать снова, повтор старого возврата всё равно
обращается к старому Loan. Проверка завершённого состояния выполняется до
изменения Item, поэтому старый запрос не может освободить или изменить новую
выдачу.

Если между изменениями Loan и Item возникает исключение, транзакция полностью
откатывается.

**Обоснование:** возврат — редкая операция с небольшой ожидаемой конкуренцией,
поэтому короткая пессимистическая блокировка конкретной выдачи даёт простой
порядок конкурентных действий.

`409` для повторного возврата выбран согласно `SR-06`: повтор считается
недопустимым переходом. Одна транзакция для Loan и Item обеспечивает конкретную
гарантию: либо одновременно записаны завершение выдачи и новый допуск предмета,
либо не записано ни одно изменение.

**Связанные угрозы:** `T-06`; частично `T-05`.

**Связанные требования:** `SR-06`, `SR-05`.

**Будущая проверка:**

- **Условие:** существует одна активная выдача и связанный Item.
- **Действие:**
  1. одновременно отправить два запроса `STAFF` на возврат одной выдачи;
  2. проверить Loan и Item в БД;
  3. повторить старый возврат после новой выдачи того же Item;
  4. в интеграционном тесте вызвать исключение между двумя изменениями
     транзакции.
- **Ожидаемый результат:** один возврат успешен, второй получает `409`; время и
  сотрудник возврата сохраняются один раз; старый повтор не меняет новую
  выдачу и Item; при искусственном исключении Loan остаётся активным, а Item —
  в прежнем состоянии.

**Ограничения и последствия:**

- все возвраты должны проходить через один транзакционный service-путь;
- внутри транзакции не должно быть медленных внешних вызовов;
- связанные операции должны придерживаться одного порядка блокировок;
- решение защищает данные через приложение и API, но не делает записи
  физически неизменяемыми для администратора PostgreSQL;
- при появлении новых состояний Loan допустимые переходы нужно пересмотреть.

## Покрытие приоритетного набора

| Приоритетная угроза | Требование | Решение | Будущая проверка |
| --- | --- | --- | --- |
| `T-01` — запрос без аутентификации | `SR-01` | `D-01` | Защищённые маршруты без principal дают `401` |
| `T-02` — обход роли `STAFF` | `SR-02` | `D-01` | `USER` не выполняет staff-only операцию даже при подставленной роли |
| `T-03` — чтение чужой выдачи | `SR-03` | `D-01` | Чужой `loanId` даёт `404`, списки содержат только свои записи |
| `T-05` — две активные выдачи | `SR-05` | `D-02` | Два параллельных запроса дают один успех и один `409`; в БД одна активная выдача |
| `T-06` — повторный или конкурентный возврат | `SR-06` | `D-03` | Один возврат фиксируется, повтор получает `409`, история не меняется |

Для всего приоритетного набора прослеживается цепочка
`T → SR → D → будущая проверка`.

## Неприоритетные угрозы и дальнейшая работа

Текущий набор D не отменяет остальные угрозы:

- `T-04` — при реализации нужны ограниченные DTO и запрет подмены серверных
  полей согласно `SR-04`;
- `T-07` частично покрывается `D-02`, но изменение допуска должно использовать
  совместимую транзакционную дисциплину;
- `T-08` требует безопасной обработки ошибок и управления секретами;
- `T-09` перед удалённым доступом потребует настройки HTTPS;
- `T-10` требует выбора password hashing согласно `SR-10`;
- `T-11` требует ограничения попыток входа согласно `SR-11`.

При уточнении реализации ID `D-*` сохраняются, пока инженерный смысл решения не
меняется принципиально.

Документ должен актуализироваться вместе с затронутыми `SR-*` и `T-*`, если меняются правила продукта.
