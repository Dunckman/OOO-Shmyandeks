# Проектные решения безопасности

Документ фиксирует проектные решения безопасности «Стафф» и
опирается на актуальные [`PROJECT.md`](../PROJECT.md),
[`docs/security-requirements.md`](security-requirements.md) и
[`docs/threat-model.md`](threat-model.md).

Текущий набор должен закрыть весь приоритетный набор угроз:

- `T-01` — доступ к защищённым данным или операциям без аутентификации;
- `T-02` — обход полномочий `STAFF`;
- `T-03` — доступ `USER` к чужой выдаче;
- `T-05` — двойная выдача одного экземпляра и частичное состояние;
- `T-06` — повторный или конкурентный возврат с искажением истории.

Будущие проверки ниже — планы проверки механизмов, а не уже выполненные тесты
или свидетельства.

В коде реализованы миграции и JPA-сущности — классы для работы с записями БД. Частичный уникальный
индекс из D-02 уже добавлен в схему. [Интеграционные тесты](../staff/src/test/kotlin/org/shmyandeks/staff/StaffApplicationTests.kt)
проверяют ограничения БД и отображение сущностей. Серверные проверки D-01,
транзакционные операции выдачи и возврата D-02/D-03 пока не реализованы.

## D-01. Единая серверная аутентификация и авторизация на объект

**Контекст:** HTTP-клиент находится за границей доверия. Пользователь может
вручную вызвать любой маршрут, изменить параметры запроса и передать поля,
которых нет в обычном интерфейсе. Поэтому наличие кнопки, указание в запросе
чужой роли или знание ID выдачи не подтверждают право доступа.

Для `T-01`, `T-02` и `T-03` сервер должен отдельно гарантировать:

1. предметный маршрут нельзя выполнить без установленной личности;
2. операции `STAFF` нельзя выполнить от имени `USER`;
3. `USER` не получает чужую выдачу даже по известному ID.

**Решение:** аутентификация и первичная проверка роли выполняются
централизованно через Spring Security до вызова предметной операции.

Сервер определяет текущего пользователя и его роль по результату
аутентификации. Эти сведения используются для проверки прав. Указанные клиентом
имя, ID пользователя или роль не могут их подменить.

Предметные маршруты закрыты по умолчанию; публичным остаётся только явно
выделенный минимальный набор, необходимый для входа и технического запуска.
Операции `STAFF` доступны только пользователю с этой ролью.

Для доступа к выдачам с ролью `USER` применяется объектная авторизация:

- в список `USER` попадают только выдачи, где он указан получателем;
- при чтении отдельной выдачи сервер одновременно проверяет её ID
  и совпадение получателя с вошедшим `USER`;
- если такой записи нет, возвращается `404`;
- `STAFF` разрешено чтение всех выдач пункта.

Без аутентификации защищённый маршрут возвращает `401`; операция, недоступная
роли вошедшего пользователя, — `403`. Запрос `USER` на чтение чужой выдачи
возвращает `404`, как описано выше.

**Обоснование:** проверка только в клиентском интерфейсе не является защитой,
потому что запрос можно сформировать вручную. Проверки только роли тоже
недостаточно: два пользователя с ролью `USER` имеют разные права на конкретные выдачи.

Централизованная политика Spring Security уменьшает риск случайно оставить
новый адрес API публичным. Условие «получатель — вошедший `USER`» включается
в запрос к БД, поэтому выборка не зависит от заявленной клиентом личности.

`404` для чужой выдачи выбран в соответствии с `SR-03`, чтобы не различать
«записи нет» и «запись существует, но принадлежит другому `USER`».

**Связанные угрозы:** `T-01`, `T-02`, `T-03`.

**Связанные требования:** `SR-01`, `SR-02`, `SR-03`.

**Будущая проверка:**

- **Условие:** в стенде есть `USER` A, `USER` B, `STAFF` и по одной активной
  и завершённой выдаче у каждого `USER`. Для активных выдач используются разные
  предметы.
- **Действие:**
  1. без аутентификации запросить каталог, выдачи и операцию `STAFF`;
  2. войти как B с ролью `USER` и вызвать операцию `STAFF`,
     указав в запросе роль `STAFF`;
  3. от имени B запросить выдачи A и свои выдачи по известным ID, проверить список B;
  4. от имени A запросить его выдачи; от имени `STAFF` прочитать выдачи A и B.
- **Ожидаемый результат:** запросы без входа получают `401` без данных; B не получает
  права `STAFF` и получает `403` без закрытых данных на операцию `STAFF`;
  чужая выдача для B даёт `404` без содержимого. Свои выдачи B получает по ID,
  а его список содержит обе собственные записи и не содержит записи A. A и `STAFF`
  получают разрешённые данные. Клиентские значения роли и пользователя не
  меняют пользователя, определённого сервером. После отказов каталог, допуск, выдачи и роли
  не меняются; новые записи не появляются.

**Ограничения и последствия:**

- новые предметные маршруты должны автоматически попадать под закрытую
  политику;
- код предметных операций не должен определять текущего пользователя и его
  роль по присланным клиентом полям;
- проверка роли не заменяет проверку получателя выдачи;
- хранение паролей и ограничение попыток входа определены в `D-05`.

## D-02. Инвариант одной активной выдачи обеспечивается транзакцией и БД

**Контекст:** обычная последовательность
«прочитать свободный предмет → проверить отсутствие активной выдачи → создать
выдачу» небезопасна при конкуренции. Два запроса могут одновременно увидеть
старое свободное состояние и оба пройти прикладную проверку. Это сценарий
`T-05`.

**Решение:** оформление выдачи выполняется одной транзакцией Spring, а
ограничение «не более одной активной выдачи на экземпляр» дополнительно
закрепляется в PostgreSQL.

Активна выдача, у которой возврат ещё не зафиксирован. В текущей схеме таблица
`loan` хранит выдачи, колонка `item_id` — ID предмета, а `returned_at` —
время возврата. Пустое время возврата (`NULL`) означает активную выдачу.
В миграции уже создан уникальный индекс:

```sql
CREATE UNIQUE INDEX uq_active_loan_per_item
    ON loan (item_id)
    WHERE returned_at IS NULL;
```

Индекс запрещает хранить две незавершённые выдачи одного предмета.
Завершённые выдачи остаются в истории и не мешают выдать предмет снова.

Операция выдачи выполняется так:

1. сервер проверяет роль `STAFF` согласно `D-01`;
2. загружает запись предмета и блокирует её для изменения в БД
   (`SELECT ... FOR UPDATE`); другой запрос изменения этой записи будет ждать;
3. под блокировкой проверяет допуск и отсутствие активной выдачи, существование
   получателя с ролью `USER` и срок позже серверного времени выдачи;
4. создаёт выдачу;
5. фиксирует транзакцию.

Операции, меняющие допуск того же предмета, также блокируют его строку
до чтения и изменения допуска и удерживают блокировку до конца транзакции.
Если два запроса всё же конкурируют на вставке, ограничение
PostgreSQL остаётся последней гарантией: одна транзакция успешна, вторая
откатывается, а клиент получает предметный `409`, а не вторую выдачу.

Внешние ключи БД проверяют существование пользователей и предмета. Роль
получателя и исполнителя, допуск предмета и запрет повторного возврата проверяет
сервер приложения в D-01–D-03. Сами по себе связи БД этих правил не обеспечивают.

**Обоснование:** транзакция обеспечивает атомарность одного запроса, но сама по
себе не гарантирует уникальность между конкурентными транзакциями. Поэтому
инвариант закрепляется на двух уровнях:

- блокировка записи предмета позволяет перепроверить состояние перед изменением;
- ограничение уникальности в БД не позволяет физически сохранить две активные выдачи.

Одной проверки отсутствия активной выдачи недостаточно: между проверкой и
сохранением другой запрос может создать такую выдачу. Синхронизация только
в памяти приложения тоже недостаточна: она не закрепляет ограничение
в хранилище и плохо переносится на несколько процессов приложения.

**Связанные угрозы:** `T-05`; дополнительно `T-07`.

**Связанные требования:** `SR-05`; дополнительно `SR-07`.

**Будущая проверка:**

- **Условие:** есть один свободный допущенный предмет и два аккаунта `USER`; тест
  выполняется с настоящим PostgreSQL.
- **Действие:** от имени одного пользователя с ролью `STAFF` одновременно отправить два запроса
  на выдачу одного предмета разным `USER`.
- **Ожидаемый результат:** ровно один запрос создаёт выдачу; второй получает
  `409`; в БД после завершения запросов существует ровно одна активная запись
  для этого предмета; внутренняя ошибка уникального индекса не раскрывается.

Дополнительно на свободном допущенном предмете проверяются оба порядка
получения блокировки при одновременной выдаче и снятии допуска:

- если сначала зафиксировано снятие допуска, выдача получает `409`, новой выдачи нет;
- если сначала зафиксирована выдача, она сохраняется, а снятие допуска применяется
  следом и запрещает следующие выдачи. Итог — одна активная выдача и предмет без допуска.

Для каждого случая готовится исходное состояние заново; порядок блокировок
в тесте задаётся явно.

**Ограничения и последствия:**

- конкурентную проверку нужно выполнять с PostgreSQL; другая тестовая СУБД
  может не подтвердить семантику частичного индекса и блокировок;
- нарушение именно ограничения одной активной выдачи должно преобразовываться в
  `409`; не любая ошибка целостности БД означает конфликт выдачи;
- блокировки могут кратковременно увеличивать задержку, что приемлемо для
  учебного пункта выдачи;
- если допустимые состояния выдачи изменятся, условие индекса нужно пересмотреть
  вместе с `SR-05` и моделью угроз.

## D-03. Возврат — однократный переход состояния в одной транзакции

**Контекст:** возврат одновременно завершает выдачу, обновляет текущее описание
состояния и дальнейший допуск предмета. Повторный, запоздалый или конкурентный
запрос не должен переписывать историю и тем более менять состояние предмета
после новой выдачи. Это
`T-06` и часть атомарности `SR-05`.

Проверки «выдача ещё активна» до сохранения недостаточно: два запроса могут
прочитать активное состояние до фиксации первого возврата.

**Решение:** возврат реализуется как один переход «активная выдача → завершённая выдача» внутри
одной транзакции.

Алгоритм:

1. сервер проверяет роль `STAFF` согласно `D-01`;
2. загружает запись выдачи с блокировкой для записи;
3. после блокировки повторно проверяет, что выдача ещё активна;
4. для активной выдачи загружает и блокирует связанный предмет;
5. сервер сам задаёт время возврата и ID выполнившего запрос `STAFF`;
6. записывает описание состояния при возврате в выдачу и то же описание —
   в карточку предмета, обновляет допуск;
7. завершает выдачу;
8. фиксирует обе части одной транзакцией.

Сохранённое в выдаче описание возврата остаётся частью истории. `STAFF` может
позже изменить текущее описание в карточке, не меняя эту запись.

Если выдача уже закрыта, операция завершается с `409` до изменения предмета. Второй
конкурентный запрос после ожидания блокировки увидит завершённое состояние и
также получит `409`.

Если предмет уже успели выдать снова, повтор старого возврата всё равно
обращается к старой выдаче. Проверка завершённого состояния выполняется до
изменения предмета, поэтому старый запрос не может освободить или изменить новую
выдачу.

Если между изменениями выдачи и предмета возникает исключение, транзакция полностью
откатывается.

**Обоснование:** возврат — редкая операция с небольшой ожидаемой конкуренцией,
поэтому короткая пессимистическая блокировка конкретной выдачи даёт простой
порядок конкурентных действий.

`409` для повторного возврата выбран согласно `SR-06`: повтор считается
недопустимым переходом. Одна транзакция для выдачи и предмета обеспечивает конкретную
гарантию: либо одновременно записаны завершение выдачи, описание состояния
и допуск предмета, либо не записано ни одно изменение.

**Связанные угрозы:** `T-06`; частично `T-05`.

**Связанные требования:** `SR-06`, `SR-05`.

**Будущая проверка:**

- **Условие:** существует одна активная выдача и связанный предмет.
- **Действие:**
  1. одновременно отправить два запроса `STAFF` на возврат одной выдачи;
  2. проверить выдачу и предмет в БД;
  3. повторить старый возврат после новой выдачи того же предмета;
  4. в интеграционном тесте вызвать исключение между двумя изменениями
     транзакции.
- **Ожидаемый результат:** один возврат успешен, второй получает `409`; время возврата и
  ID выполнившего его `STAFF` сохраняются один раз; сразу после возврата описание в карточке
  совпадает с описанием возврата в выдаче; старый повтор не меняет новую
  выдачу и предмет; при искусственном исключении выдача остаётся активной, а предмет —
  в прежнем состоянии.

**Ограничения и последствия:**

- все возвраты должны проходить через один участок кода с общей транзакцией;
- внутри транзакции не должно быть медленных внешних вызовов;
- связанные операции должны придерживаться одного порядка блокировок;
- решение защищает данные через приложение и API, но не делает записи
  физически неизменяемыми для администратора PostgreSQL;
- при появлении новых состояний выдачи допустимые переходы нужно пересмотреть.

## D-04. Раздельные модели запросов и ответов

**Контекст:** входные поля могут подменить историю (`T-04`), а прямой возврат
сущности БД — раскрыть связанный аккаунт и его хеш пароля (`T-08`).

**Решение:** для каждой операции используются отдельные структуры данных запроса
и ответа (DTO). В них перечисляются только разрешённые поля.
При выдаче принимаются получатель, предмет, срок и состояние при передаче;
при возврате — только состояние при возврате и дальнейший допуск. Остальные
поля отклоняются с `400` до изменения данных. Сервер записывает ID вошедшего
`STAFF` как исполнителя и сам задаёт время события. Получатель, предмет,
срок и состояние при передаче после оформления не меняются. Инвентарный номер
принимается только при создании карточки; попытка его изменить получает `409`.
Редактирование названия, текущего описания состояния или допуска предмета
не переписывает состояния при передаче и возврате в истории выдач.

В ответе каталога отдельно указываются допуск, наличие активной выдачи и
доступность для новой выдачи. Последние два признака вычисляются при чтении
по активной выдаче и допуску, а не хранятся как отдельные изменяемые флаги.
Предмет доступен, только если допущен и не занят. Получатель и другие сведения
о его выдачах в ответ каталога не включаются.

Для карточек, выдачи и возврата сервер проверяет обязательные поля, формат
ID и времени до записи в БД. Инвентарный номер — от 1 до 100
символов, название — от 1 до 200, как в текущей схеме. Описание состояния
в карточке, при передаче и возврате обязательно. Пустые строки и строки
только из пробелов недопустимы.

После проверки входа и полномочий ошибки обрабатываются так:

| Причина отказа | Ответ |
| --- | --- |
| Нет обязательного поля, неверный формат, пустая строка или превышена длина | `400` с указанием ошибочного поля |
| Срок возврата не позже серверного времени выдачи или получатель не имеет роли `USER` | `400` с причиной отказа |
| Не найден предмет, получатель или выдача | `404`; чужая выдача для `USER` также даёт `404` по D-01 |
| Инвентарный номер уже занят другой карточкой или запрошено изменение номера существующей карточки | `409` |
| Предмет занят, не допущен или выдача уже возвращена | `409` по D-02/D-03 |

Отказ не меняет предметные данные. Конфликт уникальности инвентарного номера
обрабатывается и при одновременном создании карточек. Остальные ошибки БД не
преобразуются автоматически в `409`.

Ответы собираются из явно разрешённых полей; объекты,
загруженные из БД, и связанные аккаунты не преобразуются в ответ целиком. Общий обработчик внутренних ошибок возвращает `500`
без SQL, стека и секретов. Пароли БД и ключи читаются из окружения или локальных
файлов вне Git; в `.env.example` остаются заглушки. Перед публикацией проверяются
подготовленные файлы и история Git на действующие секреты.

**Обоснование:** явное сопоставление полей отделяет пользовательские данные от
серверных и не добавляет новые поля сущности в API автоматически.

**Связанные угрозы:** `T-04`, `T-08`; дополнительно `T-03`.

**Связанные требования:** `SR-04`, `SR-08`; дополнительно `SR-03`.

**Будущая проверка:** на стенде с двумя аккаунтами `USER` и одним `STAFF` выполнить
сценарии `SR-04` и `SR-08`. Сравнить БД до и после подмены полей, а также выдачу
до и после редактирования карточки предмета. В ответах при обычном чтении и при
вызванной ошибке не должно быть хеша пароля или тестового секрета конфигурации.
Проверить публикуемые файлы и историю Git. Ожидаются `400` без изменений при
подмене, неизменная история и отсутствие закрытых данных в ответах и репозитории.
Дополнительно проверяются четыре сочетания допуска и занятости в каталоге:
доступен только свободный допущенный предмет; получатели не раскрываются.
Попытка сменить инвентарный номер даёт `409`, а разрешённое изменение карточки
не меняет описания состояний в истории. Для ошибок из таблицы выше проверяются
ответ и отсутствие изменений. При остальных корректных данных номер из 100
символов и название из 200 принимаются, а превышение каждого лимита на один
символ даёт `400` без изменений. При одновременном создании двух карточек
с одним номером создаётся одна карточка, второй запрос получает `409`.

**Ограничения и последствия:** при добавлении поля нужно отдельно определить,
допустимо ли принимать его от клиента или возвращать в ответе.

## D-05. Хеширование паролей и ограничение входа

**Контекст:** утечка БД позволяет подбирать пароли офлайн (`T-10`), а повторные
запросы входа — онлайн (`T-11`). Для этих случаев нужны разные меры.

**Решение:** учебные аккаунты создаются локальной командой подготовки стенда.
Пароль вводится без отображения и не записывается в SQL-файл или журнал.
Используется [Argon2PasswordEncoder из Spring Security](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html#authentication-password-storage-argon2) с Argon2id: 19 МиБ памяти,
два прохода, параллелизм 1, случайная соль 16 байт и хеш 32 байта. Это выбранный
для стенда профиль по [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#argon2id).
В БД сохраняется только строка с алгоритмом, параметрами, солью и хешем;
вход использует ту же библиотеку проверки пароля. Если лимит попыток не исчерпан,
для неизвестного логина выполняется проверка по служебному хешу с такими же
параметрами и возвращается та же ошибка `401`.

Для лимита попыткой входа считается отдельный запрос с логином и паролем.
Перед проверкой пароля сервер учитывает попытку по логину. В отдельной таблице
PostgreSQL хранится запись лимита с уникальным ключом логина и моментами
допущенных попыток. Запись создаётся при отсутствии, в том числе для неизвестного
логина. Под блокировкой этой записи сервер удаляет отметки старше или равные
60 секундам, проверяет лимит и добавляет текущую попытку в одной транзакции.
Ключ совпадает со строкой логина, по которой ищется аккаунт.
После пяти попыток возвращается `429` с заголовком `Retry-After`: в нём указано,
через сколько секунд освободится ближайшая попытка. Отказы `429` не добавляются в счётчик; успешный вход его не сбрасывает.
Лимит не затрагивает другие логины. Запросы к каталогу и выдачам не расходуют
попытки и не отклоняются из-за исчерпанного лимита входа; для них сохраняются
обычные проверки аутентификации и прав.

После запуска и далее раз в минуту приложение удаляет записи лимита, в которых
все попытки совершены не менее 60 секунд назад, а также пустые записи. Перед
удалением запись блокируется и условие проверяется заново, чтобы не удалить свежую попытку
параллельного запроса. Если запись уже удалена, новый запрос создаёт её заново
и повторяет проверку лимита. Так неиспользуемые записи не накапливаются бессрочно.

**Обоснование:** Argon2id повышает стоимость офлайн-подбора; лимит сокращает
число онлайн-попыток. Хранение счётчика в БД сохраняет его при перезапуске,
а блокировка исключает обход одновременными запросами.

**Связанные угрозы:** `T-10`, `T-11`.

**Связанные требования:** `SR-10`, `SR-11`; дополнительно `SR-01`.

**Будущая проверка:** выполнить `SR-10` и `SR-11`, проверить настройки библиотеки хеширования
и сохранённых хешей. При шести одновременных попытках одного логина к проверке
пароля допускаются не более пяти; перезапуск не обнуляет незавершённое окно.
Пять успешных входов также исчерпывают лимит. После этого запросы с действующей
аутентификацией к каталогу и своим выдачам продолжают проходить обычную проверку
доступа, а другой логин может войти. Очистка удаляет истёкшие записи и сохраняет
записи с попытками за последние 60 секунд. Одновременные очистка и новый вход
не удаляют свежую попытку и не сбрасывают действующий лимит.

**Ограничения и последствия:** намеренное исчерпание чужого лимита всё ещё
может мешать новому входу. Этот остаточный риск принят для закрытого учебного
стенда с доступом только команды согласно `D-06`; постоянной блокировки аккаунта
нет. По мере истечения 60 секунд попытки освобождаются. Такое ограничение нельзя
считать достаточным для публичного сервиса в интернете.

## D-06. Локальный запуск и защищённая передача данных

**Контекст:** клиент находится вне продукта. Даже отказ API обрабатывать HTTP
не защищает пароль, который клиент уже отправил открытым текстом (`T-09`).

**Решение:** основной стенд запускается на одном компьютере: API и порт
PostgreSQL доступны только через `127.0.0.1`. Для демонстрации с другого
компьютера используется отдельная конфигурация: [HTTPS во встроенном сервере
Spring Boot](https://docs.spring.io/spring-boot/how-to/webserver.html#howto.webserver.configure-ssl), TLS 1.2/1.3, сертификат для имени сервера с цепочкой, которой доверяет
проверочный клиент. HTTP-порт не открывается; порт БД остаётся локальным.
Сетевой доступ к API разрешён межсетевым экраном только с компьютеров команды.
Ключ сертификата и пароль хранилища не попадают в Git.

Внешний проверочный клиент обращается сразу по HTTPS, включая вход, и не
отключает проверку сертификата. Настройки клиента являются условием стенда.

**Обоснование:** локальная привязка ограничивает доступ к учебной версии,
а встроенный HTTPS не требует добавления отдельного прокси в архитектуру.
Шифрование и проверка сертификата защищают данные в сетевом режиме.

**Связанные угрозы:** `T-09`.

**Связанные требования:** `SR-09`.

**Будущая проверка:** выполнить `SR-09` отдельно для обеих конфигураций.
Локальный API недоступен с другого компьютера. В сетевой конфигурации разрешённый
клиент работает по HTTPS, посторонний компьютер не подключается. API не
обрабатывает запросы по HTTP; клиент прерывает соединение с неверным сертификатом
до отправки данных. В проверке HTTP используются только фиктивные данные.

**Ограничения и последствия:** это закрытый учебный стенд. Публичный доступ
из интернета не предусмотрен; настройки сети и доверия сертификату входят
в подготовку демонстрации, а не обеспечиваются произвольным клиентом автоматически.
